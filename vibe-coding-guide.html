You describe what you want in plain English. An AI writes the code. You test it, steer it, and ship it.

That is vibe coding. This guide teaches you to do it well: so what you build works, looks good, stays safe, and can be put in front of real people.

You do not need to know how to code. You do need patience, curiosity, and a willingness to look things up. Every unfamiliar word is explained, and every topic links to free reading if you want more.

What Is Vibe Coding

On this page

The simple version

Normally, to make an app, a person writes thousands of lines of code in a special language. With vibe coding, you describe what you want and an AI writes that code for you.

Think of it like hiring a very fast, very eager builder:

  • You are the customer and project manager. You decide what to build and whether it’s good.
  • The AI is the builder. It does the typing.
  • The builder is fast but sometimes confidently wrong. Someone must check the work. That is you.

What it is good at

  • Turning ideas into working prototypes in hours
  • Standard things: forms, login pages, dashboards, lists, simple games
  • Explaining what code does
  • Fixing errors when you show it the message

What it is bad at

  • Knowing what you meant when you were vague
  • Remembering earlier conversations
  • Noticing its own security mistakes
  • Large, tangled projects with no organization
  • Saying “I don’t know”. It will often guess instead.

Warning The core risk

AI-written code can look perfect and still be broken or unsafe. Working on your screen is not the same as safe for the public. Most of this guide exists to close that gap.

The mindset that works

  1. Small steps. Ask for one thing at a time.
  2. Test everything. Click every button yourself.
  3. Save often. Use Git so you can undo. See Git and GitHub.
  4. Keep notes. The AI forgets. Notes remember. See Project Memory Files.
  5. Learn a little. Every concept you understand makes your prompts better. See Prior Knowledge.
  6. Never trust blindly. See Reviewing AI Code.

The big picture of a project

Idea → Plan → Design → Build in small steps → Test → Secure → Launch → Maintain

Each arrow has a note in this guide. Start at Start Here.

How Websites and Apps Work

On this page

Imagine a restaurant. Every piece of software maps onto it.

Restaurant Software What it means
The dining room Frontend What people see and click: buttons, pages, colors
The kitchen Backend Hidden logic: checks passwords, calculates, decides
The waiter API Carries requests from the dining room to the kitchen and brings back answers
The pantry and filing cabinets Database Where information is stored long-term: users, orders, posts
The building and electricity Hosting The computer (server) that keeps it all running 24/7
The street address Domain name yourapp.com, the name people type
The phone book DNS Translates the name into the building’s real location
The front door lock HTTPS / SSL Scrambles traffic so strangers cannot listen in
The ID check at the door Authentication Proving who you are (logging in)
The VIP list Authorization What each person is allowed to do
The recipe book Code Instructions the computer follows
The master recipe archive with history Git / GitHub Saves every version so you can undo

What happens when someone visits your app

  1. They type yourapp.com.
  2. DNS looks up which server holds your app.
  3. Their browser asks that server for the page, over HTTPS.
  4. The server sends back the frontend (the page).
  5. They click “Sign in”. The frontend sends a request through the API to the backend.
  6. The backend checks the database: is this password correct?
  7. The backend replies “yes” and the frontend shows their dashboard.

All of that takes less than a second.

Where things live

Your laptop           →  where you build and test ("local")
GitHub                →  where your code is saved and backed up
Vercel / Cloudflare   →  where the website is served from ("hosting")
Supabase              →  where data and logins live ("backend service")
Domain registrar      →  where you bought your name

Notes: Git and GitHub, Hosting With Vercel, Cloudflare, Databases and Supabase, Domains DNS and HTTPS.

Three kinds of environments

  • Local: on your computer. Nobody else can see it. Safe to break.
  • Staging / Preview: a private test copy online.
  • Production: the real one, with real users. Treat it carefully.

Tip Rule

Never experiment on production. Experiment locally, test in preview, then release.

Glossary

On this page

Plain-English meanings. Search this note (Ctrl/Cmd + F) when you meet a word you do not know.

Building blocks

  • App: software you use. Can be a website, phone app, or desktop program.
  • Frontend: the part users see.
  • Backend: the hidden part that does the work.
  • Full-stack: frontend plus backend.
  • API: a menu of requests one program can make to another.
  • Database: organized storage for information.
  • Framework: a pre-built toolkit so you do not start from zero. Examples: Next.js, React.
  • Library / package: someone else’s code you reuse.
  • Dependency: a package your project needs.
  • npm: the store where JavaScript packages are downloaded from.
  • Component: a reusable piece of a page, like a button or card.
  • Repository (repo): a project folder tracked by Git.

Languages

  • HTML: the structure of a page.
  • CSS: how a page looks.
  • JavaScript (JS): how a page behaves.
  • TypeScript (TS): JavaScript with safety labels that catch mistakes early.
  • SQL: the language used to talk to databases.
  • Python: popular for scripts, data, and AI.

Working with code

  • Terminal / command line: a text window where you type commands.
  • IDE / editor: a program for viewing and editing code (VS Code, Cursor).
  • Git: a time machine for code.
  • Commit: a saved snapshot.
  • Branch: a separate copy to try things without risk.
  • Pull request (PR): a request to merge changes in, usually reviewed first.
  • Bug: a mistake in the code.
  • Debugging: finding and fixing bugs.
  • Console / logs: messages a program prints to explain what it is doing.
  • Stack trace: the long error message showing where something crashed.
  • Localhost: your own computer pretending to be a server, for testing.
  • Build: converting your code into the final form for hosting.
  • Deploy: publishing your build so others can use it.
  • CI/CD: automatic testing and deploying whenever you save changes.

AI words

  • Prompt: the instructions you give the AI.
  • Context window: how much text the AI can “keep in mind” at once.
  • Token: a chunk of text (roughly three quarters of a word). Limits are measured in tokens.
  • Hallucination: the AI confidently inventing something false (fake functions, fake facts).
  • Agent: an AI that can take actions (edit files, run commands), not only chat.
  • MCP (Model Context Protocol): a standard way to plug tools like Figma or databases into an AI.
  • System prompt / rules file: standing instructions the AI reads every time. See Project Memory Files.

Hosting and internet

  • Server: a computer that is always on, serving your app.
  • Serverless: hosting where you do not manage servers; it runs your code on demand.
  • CDN: copies of your site around the world so it loads fast everywhere.
  • Domain: your web address.
  • DNS: the phone book mapping names to servers.
  • SSL / TLS / HTTPS: encryption for traffic.
  • Environment variable: a secret or setting stored outside your code.
  • Uptime: the percentage of time your app is working.

Security words

  • Authentication (authn): proving who you are.
  • Authorization (authz): what you are allowed to do.
  • 2FA / MFA: a second proof beyond your password.
  • Hash: a one-way scramble used to store passwords safely.
  • Encryption: scrambling data so only the right key can read it.
  • API key: a password for a program.
  • Secret: any key, token, or password that must stay private.
  • RLS (Row Level Security): database rules about which rows each user can access. See Data Access and RLS.
  • XSS, SQL injection, CSRF: common attacks. See Common Attacks.
  • Vulnerability: a weakness an attacker could use.
  • Penetration test: hiring someone to try to break in, safely.
  • PII: personally identifiable information (names, emails, addresses).

Business words

  • MVP: minimum viable product, the smallest useful version.
  • B2C: selling to consumers (public).
  • B2B: selling to businesses.
  • SaaS: software sold by subscription.
  • SLA: a written promise about uptime and response times.
  • SOC 2: a security audit report companies often ask vendors for.
  • GDPR / CCPA: privacy laws (Europe / California).
  • Terms of Service: the rules for using your product.
  • Privacy Policy: what you collect and why.

Warning Turn on 2FA everywhere, today

Do this on email, GitHub, Supabase, Vercel, Cloudflare, and your domain registrar. These accounts control your product.

2. Software to install

  • Obsidian: your notes. See Notes With Obsidian.
  • A code editor: VS Code or Cursor. This is where you see your files.
  • Node.js (LTS version): runs most modern web projects. nodejs.org
  • Git: git-scm.com
  • A browser with developer tools: Chrome, Firefox, or Edge. Press F12 to open them.

3. Pick an AI coding tool

There are two kinds:

Chat tools. You paste code back and forth in a chat window. Easiest start, most manual.

Agent tools. The AI reads your whole project, edits files, and runs commands. Faster, but it can also break more at once. Examples include Claude Code and AI-enabled editors.

  • Claude Code docs

Tip Advice

Begin with a chat tool or an agent in a throwaway project. Move to agent tools once Git saves are a habit.

4. Folder habits

Make one folder for all projects, one subfolder per project:

Projects/
  my-first-app/
    CLAUDE.md
    SPEC.md
    PLAN.md
    src/

Never store projects inside a cloud-synced folder like Dropbox or OneDrive. Syncing thousands of tiny files causes problems. Use Git instead.

5. Your first five minutes

  1. Create a project folder.
  2. Open it in your editor.
  3. Run git init in the terminal.
  4. Create a README.md and a .gitignore file (see Secrets and API Keys).
  5. Commit: git add . then git commit -m "start".

Prompting Basics

On this page

A prompt is your instruction to the AI. Better instructions, better results. Think of it as briefing a smart new employee who knows nothing about your project and cannot ask follow-up questions as fast as you can type.

The six ingredients

  1. Goal: what you want, in one sentence.
  2. Context: what already exists. What is this project? What tools does it use?
  3. Details: exact behavior. “When the user clicks Save, show a green message that says Saved.”
  4. Constraints: limits. “Do not add new packages.” “Keep it to one file.”
  5. Examples: show what good looks like.
  6. Output format: “Explain first, then change code.” “Show only the changed lines.”

Example Weak vs strong

Weak: “make a login page”

Strong: “In my Next.js app, add a /login page with email and password fields and a Sign In button. Use Supabase Auth, which is already set up in lib/supabase.ts. Show a red error message under the form if login fails. Match the style of the existing /signup page. Do not change any other files.”

Golden rules

1. Ask for a plan before code

“Before writing any code, tell me your plan in numbered steps. Wait for me to approve.”

This catches wrong assumptions cheaply.

2. One task per prompt

“Add login, a dashboard, payments, and dark mode” fails. Do them one at a time. See The Build Loop.

3. Say what NOT to do

AI loves to “helpfully” rewrite things. Add: “Only change what I asked. Do not refactor, rename, or delete anything else.”

4. Be specific about what you see

Instead of “it’s broken”, say: “When I click Save, nothing happens. The browser console shows: TypeError: x is undefined at form.js:42.”

5. Ask it to explain

“Explain this in simple terms, as if to a beginner.” Understanding what was built protects you.

6. Make it check itself

“Before you finish, list anything you assumed, and anything that could break.”

7. Give it the real information

Paste the real error, real file, real data shape. Never paraphrase an error.

8. Ask for options when unsure

“Give me 3 ways to do this, with pros and cons for a beginner. Recommend one.”

9. Do not paste secrets

Never put passwords, API keys, or customer data in a prompt. See Secrets and API Keys.

10. Verify claims

If the AI says “this package does X” or “this setting exists”, confirm in the official docs. See Reviewing AI Code.

Useful phrases

Situation Say
Starting “Don’t write code yet. Ask me clarifying questions first.”
Vague idea “Interview me one question at a time until you can write a spec.”
Too big “Break this into the smallest steps that each can be tested.”
It’s guessing “If you’re not sure, say so. Do not invent.”
Wants to rewrite “Minimal change only.”
Confusing code “Explain what this file does, line by line.”
Finishing “Summarize what changed so I can write it in my notes.”

Role prompts

Telling the AI who to be sharpens the answer:

  • “Act as a senior security engineer reviewing this code for vulnerabilities.”
  • “Act as a patient teacher for a complete beginner.”
  • “Act as a skeptical product manager. What is missing from my spec?”

Match the model to the job

Larger, smarter models cost more and are slower. Use them for planning, architecture, and hard bugs. Use smaller, faster ones for simple edits.

Project Memory Files

On this page

The problem

The AI has no memory between conversations, and even inside one long conversation it gradually loses track. Each new chat is a stranger.

The solution

Keep a small set of plain text files in your project that describe it. Give them to the AI at the start of every session. Many tools read certain files automatically.

You write these in Obsidian or your editor. They are normal .md (Markdown) files, a simple text format where # makes a heading and - makes a bullet.

The files

File Purpose Update when
README.md What this project is and how to run it Setup changes
SPEC.md What the product must do, and for whom The idea changes
PLAN.md Checklist of steps, done and to-do After every step
CLAUDE.md (or AGENTS.md / rules file) Standing instructions to the AI You learn a new rule
DECISIONS.md Choices made and why You decide something
BUGS.md Known problems and fixes A bug appears or is fixed
.env.example Names of secrets needed (no values) You add a secret

Tip Which file the tool reads

Claude Code reads CLAUDE.md automatically. Other tools use AGENTS.md, .cursorrules, or similar. Check your tool’s docs, or ask: “What file do you read for standing project instructions?”

What goes in the rules file

Keep it short, clear, and about this project.

# Project: Pet Sitter Booking App

## What this is
Website where pet owners book sitters. Built for non-technical users.

## Tech stack
- Next.js (App Router), TypeScript
- Supabase for database and login
- Deployed on Vercel

## Rules
- Make the smallest change that works. Do not refactor unrelated code.
- Never put secrets in code. Use environment variables.
- Every database table must have Row Level Security.
- Ask before adding a new package.
- After each task, update PLAN.md and tell me what to test.

## How to run
npm install
npm run dev   (opens at localhost:3000)

## Style
- Friendly, simple wording
- Colors and spacing defined in /styles/tokens.css. Reuse them.

What goes in the spec

# Spec
## Goal (one sentence)
## Who uses it
## Must-have features (numbered)
## Nice-to-have (later)
## Out of scope (what we will NOT build)
## Data it stores
## Security needs
## Success looks like

“Out of scope” is powerful: it stops the AI from adding extras.

What goes in the plan (checklist method)

# Plan
- [x] 1. Create project and push to GitHub
- [x] 2. Home page layout
- [ ] 3. Sign up and login
- [ ] 4. Create booking form
- [ ] 5. Booking list page
- [ ] 6. Security review

Ask the AI: “Do step 3 only. When done, tick it off in PLAN.md.” This keeps both of you on track and lets you restart a conversation anytime. See When to Start a New Conversation.

The decision log

## 2025-03-02: Use Supabase Auth, not custom login
Why: Safer. Passwords are hard to store correctly.
Rejected: Writing our own login.

Six months later, you (and the AI) will know why.

The handoff note

End a long session with:

“Write a handoff note: what we built, what’s done, what’s next, any traps. I will paste it into a fresh conversation.”

Save it in Obsidian. Start the next chat with it.

Obsidian tip

Keep the vault folder for each project beside the code, or link to it. Use double-bracket links between Spec, Plan, and Decisions. Templates are in Templates.

When to Start a New Conversation

On this page

Why it matters

An AI conversation is like a whiteboard. Every message adds writing. Eventually the board is full, messy, and contradictory. The AI starts to forget early details, repeat itself, or mix up old and new code. This limit is the context window.

Start fresh when…

Signal What it looks like
New task You finished login. Now you want payments. Different job, new chat.
It repeats itself Same fix, same error, again and again.
It forgets Ignores rules you set earlier. Re-introduces bugs you fixed.
Conversation is very long Dozens of back-and-forths, huge pasted files.
It is confidently wrong Invents functions or files that do not exist.
You went down a wrong path Several failed attempts. The chat is “polluted” with bad ideas.
Coming back later New day, new session. Do not assume it remembers.
Switching roles Done building, now want a security review. A fresh reviewer is more critical.

Stay in the same conversation when…

  • You are mid-task and things are working.
  • The next question depends on the last answer.
  • Only a few messages have passed.

How to restart without losing progress

  1. In the old chat, ask: “Write a handoff note: goal, what’s done, what’s in progress, key decisions, known bugs, next step.”
  2. Save it in Obsidian.
  3. Make sure your files are up to date: PLAN.md, DECISIONS.md. See Project Memory Files.
  4. Commit your code with Git. See Git and GitHub.
  5. Open a new chat. Paste:
    • the rules file (or let the tool read it)
    • the handoff note
    • only the files relevant to the next task
  6. Ask: “Summarize your understanding of the project and next step before doing anything.” Correct it if wrong.

The “stuck bug” reset

If you have failed to fix the same bug three times:

  1. Stop.
  2. Revert to the last working commit (git restore . or checkout).
  3. New chat.
  4. Describe the bug from scratch: what you expected, what happens, exact error, the one relevant file.
  5. Ask for three possible causes before any code.

Fresh context often solves in one message what the old chat could not in twenty.

One conversation per…

  • Feature (best habit)
  • Bug
  • Review (security, design, performance)

Tip Rule of thumb

If you cannot remember what you asked at the start, the AI cannot either.

The Build Loop

On this page

Professionals do not build everything at once. They repeat a small loop. So should you.

Plan → Build one small piece → Test → Save → Update notes → Repeat

Step by step

1. Plan

Write the goal in SPEC.md. Break it into small steps in PLAN.md. Each step should be something you can test in under a minute. See Project Memory Files.

2. Build one piece

Prompt for one step only.

“Do step 4 of PLAN.md only. Tell me what you changed and how to test it.”

3. Test it yourself

  • Run the app.
  • Click the thing you built.
  • Try it wrong on purpose: empty fields, very long text, weird characters.
  • Check the browser console (F12) for red errors.
  • Test on your phone too.

4. Save

Commit with Git. A clear message: add booking form. If something breaks later you can return here. See Git and GitHub.

5. Update notes

Tick off the step. Record any decision or bug. Two minutes now saves an hour later.

6. Repeat

Next step. Consider a new conversation if the chat is long. See When to Start a New Conversation.

Order of work for a whole project

  1. Skeleton: empty pages and navigation, no features.
  2. Design: colors, fonts, layout. See Design Systems and Prompting.
  3. Data: tables and structure. See Databases and Supabase.
  4. Login: before anything private. See Accounts and Login.
  5. Core feature: the one thing the product exists to do.
  6. Secondary features.
  7. Security pass: see Security Checklist.
  8. Polish: errors, empty states, loading states, mobile.
  9. Deploy: see Hosting With Vercel.
  10. Launch: see Launch Checklist.

Warning Common beginner trap

Building twelve features before testing any. Then nothing works and nobody knows why. Test after every step.

Branch for risky changes

Before a big change: git checkout -b try-new-layout. If it goes badly, delete the branch. Main stays safe.

Checkpoints

Every few steps, stop and ask the AI:

“Review the whole project so far. What is inconsistent, duplicated, or fragile? Do not change anything yet. List problems by priority.”

Debugging With AI

On this page

A bug is when software does something other than what you wanted. Bugs are normal. Even experts spend much of their time on them.

Read the error

Errors look scary but usually say exactly what is wrong.

TypeError: Cannot read properties of undefined (reading 'name')
    at ProfileCard (src/components/ProfileCard.tsx:14:22)

Translation: “On line 14 of ProfileCard.tsx, the code tried to read name from something that does not exist.”

Read: (1) the first line, (2) the file and line number.

Where to find errors

Place How
Browser console Press F12, open Console
Terminal running your app Look where you typed npm run dev
Network tab F12, Network, look for red or failed requests
Hosting logs Vercel or Cloudflare dashboard, Logs
Database logs Supabase dashboard, Logs

The bug report prompt

Always give the AI these five things:

1. What I wanted to happen:
2. What actually happens:
3. Exact error message (copy and paste):
4. Steps to reproduce:
5. What I already tried:
Relevant file(s): (paste them)

The debugging ladder

  1. Re-read the error and paste it exactly.
  2. Ask for causes first: “List 3 possible causes, most likely first. Don’t change code yet.”
  3. Test the likeliest cause with the smallest possible change.
  4. Add logging: “Add console.log lines so we can see the values at each step.”
  5. Isolate: “Make the smallest example that reproduces the bug.”
  6. Revert if it got worse. Use Git. See Git and GitHub.
  7. Reset the conversation after three failed tries. See When to Start a New Conversation.

Traps

  • Fix piles. The AI stacks patch on patch. Revert and ask for the root cause.
  • Fake fixes. It hides the error instead of solving it (for example, wrapping everything in try/catch). Ask: “Does this fix the cause or just silence the error?”
  • Invented functions. If an error says something “is not a function”, the AI may have used a function that does not exist. Check the docs.
  • Outdated advice. Libraries change. Say which version you use.
  • Works locally, fails online. Usually a missing environment variable or different settings. See Secrets and API Keys.
  • Changing too much. Say “minimal change only”.

Rubber duck method

Explain the bug aloud to the AI (or a rubber duck) in plain words. Half of bugs reveal themselves while explaining.

When to stop and get a human

  • Anything involving money, passwords, or others’ private data that you cannot get to work safely
  • Same bug, many resets
  • Strange security behavior

Communities: Stack Overflow, GitHub Issues for the library, official Discords.

Decision questions

Personal Projects

On this page

Tools for yourself, family, or friends: a budget tracker, a recipe book, a workout log, a game, a family photo page, a home automation dashboard.

Priorities (in order)

  1. It works for you. Solve your own problem.
  2. Learn. Use projects to build understanding. Ask the AI to explain.
  3. Keep secrets safe. Even personal projects leak keys. See Secrets and API Keys.
  4. Save with Git. Free insurance. See Git and GitHub.
  5. Keep it simple. Fewer features, fewer bugs.
  6. Speed over polish. Ship an ugly version that works.

What you can skip

  • Elaborate legal pages (if nobody else uses it)
  • Heavy monitoring
  • Complex roles and permissions
  • Perfect design
  • Load testing

What you must NOT skip

  • Never commit API keys or passwords.
  • Use strong, unique passwords and 2FA on the accounts it uses.
  • If it is on the internet, add login. Do not leave private data open to anyone with the link.
  • Back up anything you care about. See Backups and Recovery.
  • If others (even friends) put data in, protect it. See Privacy and Legal.

Tool suggestions

  • Runs only on your computer? No hosting needed. Open localhost.
  • Share with family? Free tiers of Hosting With Vercel or Cloudflare Pages.
  • Needs data? Databases and Supabase free tier, or a local file for tiny projects.
  • Needs login? Supabase Auth. See Accounts and Login.

  1. Write 5 lines in SPEC.md: what it does, who uses it.
  2. Prompt: “Build the simplest working version, one file if possible.”
  3. Test and use it for a week.
  4. Note annoyances in BUGS.md. Fix the top three.
  5. Stop. Finished is better than perfect.

Great first projects

  • To-do list with saved data
  • Habit tracker
  • Flashcard quiz
  • Recipe organizer

  • Personal website or portfolio
  • A small game

Warning signs you should upgrade your approach

  • A friend of a friend asks to use it

Commercial Products

On this page

Products sold or offered to the general public: a subscription app, an online store, a tool with a free and paid tier, a mobile game, a marketplace.

Strangers trust you with their time, their data, and their money. That is a responsibility.

Priorities (in order)

  1. Security of user data and money. One breach can end a young product. See Security Checklist.
  2. Core value. Does it solve a real problem better than alternatives? Talk to real users early.
  3. Reliability. If it is down, customers leave.
  4. Legal basics. Terms, Privacy Policy, payments rules. See Privacy and Legal.
  5. Simple, clear design. Strangers will not figure out a confusing app. See Design Basics.
  6. Speed to first users. An MVP in weeks beats a perfect product in a year.
  7. Cost control. Know what each user costs you. See After Launch.
  8. Support. Someone must answer when things go wrong.

Build checklist

Money rules

  • Use Stripe (or similar). They handle card data; you never see it.
  • Verify payments on the server, not only in the browser. Anyone can fake the browser. See Common Attacks.
  • Keep prices in one place on the server.
  • Plan for refunds, failed payments, and cancellations.

Business basics

  • Who is your customer? Be specific.
  • How do you earn? Subscription, one-time, ads, usage-based.
  • Costs: hosting, database, AI fees, domain, email, payment fees, your time.
  • Legal entity and taxes: talk to an accountant or lawyer in your region. This guide is not legal advice.

Launch gradually

  1. Private test with friends
  2. Closed beta (invite list)
  3. Public launch with limits
  4. Grow, fix, repeat

Fake payments Verify on the server
Bill shock (AI or cloud costs) Usage limits and alerts
Bot signups and spam Turnstile, rate limits

Company Products

On this page

Software you build for or sell to a business: an internal tool, a dashboard for a client, a SaaS for companies, a custom automation. This is called B2B (business to business).

Companies pay more, but they demand more: proof of security, reliability, and professionalism. They will ask hard questions before signing.

Priorities (in order)

  1. Trust and security. Companies hold their customers’ and employees’ data. A weak vendor is a liability. See Security Checklist.
  2. Reliability and honesty. Promise only what you can deliver. Under-promise.
  3. Data separation. Company A must never see Company B’s data. This is called multi-tenancy. See Data Access and RLS.
  4. Roles and permissions. Admin, manager, member, viewer.
  5. Audit trail. A log of who did what, when.
  6. Documentation and support. Setup guides, a contact, response times.
  7. Compliance. Often asked: SOC 2, GDPR, data processing agreements. See Privacy and Legal.
  8. Integration. Works with their existing tools (Google, Microsoft, Slack, spreadsheets).
  9. Polish. Companies judge you by professionalism.

What companies will ask you

Expect a security questionnaire. Typical questions:

  • Where is data stored and who can access it?
  • Is data encrypted in transit and at rest?
  • How do you handle logins? Do you support SSO and 2FA?
  • Do you have backups? How fast can you restore?
  • What happens in a breach? Who gets told, and when?
  • Do you test for vulnerabilities?
  • Do you use subcontractors (AI providers, hosting)? Which?
  • Can we export or delete our data?
  • Do you have insurance or certifications?

Prepare short, honest written answers ahead of time. Keep them in a note.

Must-have features

Be careful with AI use

If your product sends customer data to an AI provider, tell customers. Check the provider’s data-use terms. Many companies forbid sending sensitive data to AI services.

Contracts and promises

  • SLA: a promise like “99.9% uptime”. Do not promise what you cannot monitor.
  • Data Processing Agreement (DPA): often required under privacy laws.
  • Terms and liability limits: get a lawyer to review before signing.
  • Support hours: state them clearly.

Working with a client

  1. Written scope: exactly what you will build.
  2. Written ownership: who owns the code and data.
  3. Milestones with demos.
  4. Written approval at each milestone.
  5. Handover: documentation, credentials transferred safely, access removed afterwards.
  6. Maintenance agreement: who fixes bugs after launch, and for how much?

Warning Vibe-coded products and company data

You are responsible for what you ship even if an AI wrote it. Before real company data touches your product, run the full Reviewing AI Code process and consider a professional security review.

Design Basics

On this page

AI-built apps tend to look generic: the same gradient, the same cards, the same centered column. The cause is usually defaults you never changed, not the code. Good design is taste plus a few simple rules, and taste is just noticing a default and overriding it.

Tip Do the checklist

Making It Not Look Vibe-Coded gives eight quick checks and a prompt for each. Run it before every launch.

1. Hierarchy: what matters most?

People scan, they do not read. Make the most important thing the biggest, boldest, or most colorful. Make secondary things quieter.

  • One primary button per screen.
  • Headings clearly larger than body text.
  • Group related things together.

2. Spacing

Cramped looks cheap. Space looks calm.

  • Pick a spacing scale: 4, 8, 12, 16, 24, 32, 48, 64 pixels.
  • Use only those numbers.
  • More space between groups than inside groups.

3. Typography

  • One or two fonts maximum. Google Fonts has free options.
  • Body text: 16 pixels or larger.
  • Line height about 1.5 for paragraphs.
  • Line length 50 to 75 characters.
  • Limit sizes to a scale (for example 14, 16, 20, 24, 32, 48).

4. Color

  • One primary color, one accent, plus neutrals (white, grays, near-black).
  • Define meaning colors: red for errors, green for success, amber for warnings.
  • Do not use more than 3 or 4 colors in one screen.
  • Never use pure black (#000) on pure white. Use dark gray.
  • Tools: Coolors, Realtime Colors.

5. Contrast

Text must be readable. Aim for a contrast ratio of at least 4.5:1 for body text.

  • Check: WebAIM Contrast Checker
  • See Accessibility.

6. Consistency

Same thing, same look, everywhere. All primary buttons identical. All cards with the same corner radius. This is what a design system gives you. See Design Systems and Prompting.

7. Alignment and grids

Line things up. Use a grid with consistent margins. Misalignment screams amateur.

8. Feedback and states

Every interactive thing has states:

  • Default, hover, pressed, focused, disabled
  • Loading (spinner or skeleton)
  • Empty (“No bookings yet. Create your first one.”)
  • Error (clear, kind, tells how to fix)
  • Success (confirmation)

AI often forgets loading, empty, and error states. Ask for them explicitly.

9. Mobile first

Most visitors use phones. Design the small screen first, then expand.

  • Buttons at least 44 pixels tall.
  • No tiny links close together.
  • Test with real phone.

10. Simplicity

Remove things. Every element should earn its place. If a screen has five goals, split it.

11. Write well

  • Buttons: verbs. “Save changes”, not “Submit”.
  • Errors: say what happened and how to fix it. “That email is already registered. Try logging in.”
  • Be human and short.
  • Never leave placeholder voice (“Submit”, “Error”, “No data found”). See Making It Not Look Vibe-Coded.

The defaults that give AI apps away

Default Do this instead
Purple-to-blue gradient One flat brand color plus one accent
Emoji as icons One icon set, same size and weight
Everything centered Grid, aligned edges, left-aligned paragraphs
One font, one weight Big bold headings, quiet body text
Only the “full data” screen designed Empty, loading, and error states too
AI images with odd hands or plastic sheen Real photos, or no image
Uniform spacing A spacing scale with more room for what matters
“Submit”, “Error”, “No data found” Messages that say what happens

Details and prompts: Making It Not Look Vibe-Coded.

Finding inspiration

  • Mobbin (real app screenshots)
  • Dribbble, Behance
  • Look at products you admire. Ask: what do they do with spacing, color, and type?
  • Save screenshots in your Obsidian notes and describe what you like.

Telling the AI what you want

Vague: “make it look modern.” Better: “Clean, spacious layout. White background, one deep green accent, rounded corners (12px), Inter font, generous spacing, subtle shadows. Style like a calm meditation app.”

Give 2-3 adjectives, a reference product, and your tokens. See Design Systems and Prompting.

Making It Not Look Vibe-Coded

On this page

You shipped something. It works. Then you hold it next to a real product and something feels off. You cannot name it, but it looks like AI made it.

The code is usually fine. What gives it away is the defaults you never changed. Every AI tool starts you from the same template. If you leave it alone, your app wears the same uniform as thousands of other weekend builds.

Tip Taste is a habit, not a gift

Taste is noticing a default and overriding it. This is the last 20% of the work that most people skip. The defaults get you to “it works”. Overriding them gets you to “this looks real”.

The eight checks below come from a guide on Creative Mind Habits. Each one has a prompt you can paste into your AI tool.

1. Kill the gradient hero

The tell: a purple-to-blue gradient background. It is the unofficial “made with AI” flag, and the first thing people notice.

The fix: pick one real brand color and commit to it. A flat background with one good accent beats a gradient every time.

Replace every purple-to-blue gradient with a flat background in my brand color and one accent. If I have not given you a brand color, ask me before choosing.

More: How to remove the purple gradient hero.

2. Emoji are not icons

The tell: a rocket emoji in the navigation bar, sparkles on buttons.

The fix: use one real icon set (Lucide, Heroicons, or similar) and use it the same way everywhere: same size, same line weight, same family. The consistency is the whole point. Give icon-only buttons a text label for screen readers. See Accessibility.

Replace every emoji used as an icon with icons from one library, all the same size and stroke weight. Keep a text label on every icon-only button.

3. Stop centering everything

The tell: one column, everything stacked and centered, floating in the middle of the screen.

The fix: give the page real layout. Use a grid, align things to an edge, and left-align paragraphs so people can actually read them. Centered text is fine for a short heading, not for body copy.

Rework the layout so it uses a grid or edge-aligned structure. Left-align all body text. Keep centered text only for short headings.

4. One font, one weight means no hierarchy

The tell: everything is the same font at the same size and weight, so the eye has nowhere to land.

The fix: you do not need five fonts. You need contrast: a big bold thing, a small quiet thing, and a clear gap between them. Optionally add one font with character for headings only.

Create a type scale: large bold headings, smaller quieter body text, clear size steps between levels. Use at most two fonts, and the second only for headings.

5. Design the empty state and the loading state

The tell: the app looks great in the demo because the demo is full of perfect data. Then a real user sees a blank screen, a spinner that never ends, or an empty list.

The fix: design the zero state: what someone sees before they have done anything. Design the loading state too. Fixing these jumps you a whole tier.

State Ask yourself
Empty What does a brand-new user see? What is the one next step?
Loading Is there a skeleton or message that shows progress?
Error Does it say what went wrong and how to fix it?
Slow or offline Does the app fail kindly?

For every screen that shows data, design three states: empty (with a clear next step), loading, and error. Show me each.

6. The AI hero image is showing

The tell: wonky hands, children with the wrong number of fingers, that plasticky AI sheen. People recognize it instantly now.

The fix: use real photography, skip the image, or generate with real guardrails. The author of the source guide wrote rules into every image prompt for a classroom app: no screens or devices, blank whiteboards, and firm limits on anatomy. The guardrails are the work.

Find every AI-generated image in the project and list any that show obvious tells so I can replace or remove them. Do not generate new people.

Also check image licensing. See Canva Workflow.

7. Let it breathe

The tell: spacing that is either cramped or weirdly uniform, with everything the same distance from everything else.

The fix: pick a rhythm and use a spacing scale (see Design Systems and Prompting). Give important things more room. White space reads as confidence: it tells people you decided what matters.

Apply one spacing scale across the app (4, 8, 12, 16, 24, 32, 48, 64 pixels). Give the most important elements the most space.

8. Write the microcopy like a person

The tell: a bare “Submit”, “Error”, or “No data found”. That is placeholder voice, and it leaks.

The fix: write buttons, errors, and empty states the way you would say them aloud, in one voice throughout. It is free and almost nobody does it.

Placeholder Human
Submit Send my booking
Error That didn’t save. Check your connection and try again.
No data found Nothing here yet. Add your first note to get started.

Rewrite all button labels, error messages, and empty-state text so each says what will happen or what to do, in a warm, direct voice.

The secret weapon: one handmade detail

One move does more than all eight checks combined: add one small thing no default would ever give you, something a human clearly built on purpose.

In the source guide’s classroom app, student avatars sit on tiny oval cushions drawn by hand in CSS. Nobody would miss them if they were gone, but no starter template would produce them. The moment someone notices, the whole app reads as made by a person who cared.

You do not need a hundred of these. You need one. Ideas:

  • A custom illustration style or mascot
  • A signature animation on the main action
  • A hand-drawn underline or shape in the header
  • Personality in a loading message
  • A distinctive way of showing progress

Suggest five small, handmade-feeling details that fit my product’s personality. Describe each in one line and how hard it is to build. Do not build any yet.

The master prompt

Paste this into any AI coding tool to run all eight checks in one go.

My app works, but it looks like a default AI-built app. Review the interface for the common giveaways below and fix them one at a time, without changing what the app does.

1. Gradients: replace any purple-to-blue gradient background with one flat brand color and a single accent. Ask me for the color if I have not given one.
2. Icons: replace emoji used as icons with one icon library (for example Lucide or Heroicons), the same size and stroke weight everywhere.
3. Layout: stop stacking and centering everything. Use a grid or edge-aligned layout and left-align paragraphs.
4. Hierarchy: set a type scale with big bold headings, smaller quieter body text, and clear steps between sizes.
5. Zero and loading states: design what a new user sees before any data exists, and what appears while content loads.
6. Images: list any AI-generated images with obvious tells (odd hands, plastic sheen) so I can replace or remove them.
7. Spacing: apply one spacing scale and give the most important elements the most room.
8. Copy: rewrite placeholder wording (generic button labels, bare error messages, "no data" text) so every message says what happens, in a human voice.

First list what you find for each point, with file names. Then fix them in that order and show me each change.

Figma Workflow

On this page

Figma is a design tool in your browser. You draw screens before building them. Think of it as an architect’s blueprint.

Why design first?

Changing a drawing takes seconds. Changing built software takes hours. A clear design also gives the AI a precise target instead of guessing.

Core ideas

Word Meaning
Frame A screen or section (like a phone screen)
Component A reusable piece (a button)
Variant A version of a component (primary, secondary, disabled)
Auto layout Boxes that stretch and space themselves like real web pages
Variables Stored colors, spacing, and text values (your design tokens)
Prototype Clickable mockup linking screens
Dev Mode A view that shows measurements and code hints for builders

Workflow

  1. Start with words. Write your spec first. See Project Memory Files.
  2. Sketch wireframes. Boxes and labels only, black and white. Decide layout before color.
  3. Set up variables. Colors, text sizes, spacing. See Design Systems and Prompting.
  4. Build components. Button, input, card, navbar.
  5. Assemble screens. Desktop and mobile.
  6. Prototype. Click through. Fix confusing flows.
  7. Hand to AI. See below.

Connecting Figma to your AI

Figma offers a connection (an MCP server) that lets compatible AI tools read your designs directly. The AI can then see frame sizes, colors, text, and components instead of guessing from a screenshot.

Typical steps:

  1. Check your AI tool’s docs for “Figma MCP”.
  2. Sign in to Figma when prompted.
  3. Copy the link to a frame (right-click the frame, choose copy link).
  4. Prompt:

“Implement this Figma frame: [link]. Use my existing components and design tokens. Make it responsive. Do not hardcode colors or sizes. Tell me what you could not match.”

If you do not have the connection, export a screenshot and paste it with a clear description. Less accurate, but works.

  • Color and contrast checkers (look for “Stark” or “A11y”)
  • Icon libraries

  • Name your layers and frames clearly. The AI reads names.

Figma’s Community has free UI kits and templates. Start from one, change colors and fonts, make it yours.

Design Systems and Prompting

On this page

A design system is a small rulebook that keeps everything consistent: colors, fonts, spacing, and components. It is the single best way to stop AI-built apps from looking like a patchwork.

Design tokens

Tokens are named values stored in one place. Change them once, the whole app updates.

:root {
  /* Colors */
  --color-primary: #1F7A5C;
  --color-primary-hover: #176148;
  --color-bg: #FAFAF7;
  --color-surface: #FFFFFF;
  --color-text: #1D2421;
  --color-muted: #5E6B66;
  --color-error: #B3261E;
  --color-success: #2E7D32;

  /* Type */
  --font-body: "Inter", system-ui, sans-serif;
  --text-sm: 0.875rem;
  --text-md: 1rem;
  --text-lg: 1.25rem;
  --text-xl: 1.75rem;

  /* Spacing */
  --space-1: 4px;
  --space-2: 8px;
  --space-3: 16px;
  --space-4: 24px;
  --space-5: 40px;

  /* Shape */
  --radius: 12px;
}

You do not need to understand every line. You need to know: tell the AI to use these, never hardcode values.

Components to define first

Button (primary, secondary, danger, disabled), text input, label, error text, card, navbar, modal, table, toast message.

Component libraries

Pre-built, well-tested pieces. They save time and are usually accessible.

  • shadcn/ui: beautiful copy-in components for React. ui.shadcn.com
  • Tailwind CSS: fast styling with small classes. tailwindcss.com
  • Radix UI, Headless UI: accessible behavior without styling.

Prompt: “Use shadcn/ui components. Do not build custom buttons or inputs.”

A design brief prompt

Design brief:
- Product: [what it is]
- Audience: [who]
- Feeling: [3 adjectives, e.g., calm, friendly, trustworthy]
- Reference: [a product whose style you like]
- Colors: use tokens in styles/tokens.css
- Font: Inter
- Layout: generous whitespace, max width 1100px, 12px corner radius
- Must include states: loading, empty, error
- Mobile first, responsive
- Do not use gradients or purple unless I ask

Avoiding “AI look”

The full checklist is in Making It Not Look Vibe-Coded. In short:

  • Use one flat brand color. Skip the purple-to-blue gradient.
  • Use one icon set. Emoji are not icons.
  • Design empty and loading states, not only the full-data screen.
  • Add one handmade detail no template would give you.
  • Give a specific style direction.
  • Ask for fewer elements.
  • Use real photos or your own illustrations.
  • Write real copy, not “Lorem ipsum”.
  • Reject generic hero sections. Describe what is unique about your product.
  • Compare against a real product you admire.

Design review prompt

Review this screen as a senior designer. Critique hierarchy, spacing, contrast, consistency with tokens, mobile layout, and missing states. List fixes by impact. Do not change code yet.

Keep design notes

In Obsidian, keep a Design note per project: tokens, screenshots, reference products, what to avoid. Paste it into new chats. See Project Memory Files.

Accessibility

On this page

Accessibility (a11y) means people with disabilities can use your product: people who are blind, color-blind, deaf, have limited hand movement, or have trouble focusing. It also helps everyone: bright sunlight, broken wrists, slow connections.

In many places it is also a legal requirement for public-facing and company products.

The big checks

  1. Contrast. Text readable against the background. Ratio at least 4.5:1.
  2. Don’t use color alone. Do not show errors only in red. Add an icon and words.
  3. Keyboard. Try using your whole app with only the Tab, Enter, Space, and arrow keys. You should see where you are (a visible focus outline).
  4. Labels. Every form field has a visible label. Placeholder text is not a label.
  5. Alt text. Meaningful images get a short description. Decorative images get empty alt text.
  6. Headings. One h1, then logical h2, h3. Do not choose headings by size.
  7. Click targets. At least 44 pixels.
  8. Zoom. The page works at 200% zoom.
  9. Motion. Respect “reduce motion” settings. No flashing content.
  10. Captions. Video needs captions, audio needs transcripts.
  11. Readable language. Short sentences, plain words.
  12. Errors help. Say what is wrong and how to fix it.

How to test (free)

  • Press Tab through the page.
  • Browser Lighthouse audit (F12, Lighthouse tab).
  • WAVE browser extension.
  • axe DevTools extension.
  • Turn on a screen reader: VoiceOver (Mac, iPhone), Narrator (Windows), TalkBack (Android).
  • Use your browser’s high contrast and zoom features.

Prompt for the AI

Make this accessible to WCAG 2.2 AA. Use semantic HTML (button, nav, main, label), visible focus states, sufficient contrast, ARIA only where needed, and alt text. List what you changed.

Tip Use real HTML elements

A <button> is accessible for free. A clickable <div> is not. AI sometimes makes clickable divs. Ask it not to.

Git and GitHub

On this page

What they are

  • Git is a time machine for your code. It saves snapshots (commits) so you can go back.
  • GitHub is a website that stores your Git history online: backup, sharing, and the link to hosting.

Without Git, one bad AI change can destroy a working project with no way back. This is the most important safety net you have.

Essential commands

Goal Command
Start tracking a folder git init
See what changed git status
Stage everything git add .
Save a snapshot git commit -m "describe the change"
See history git log --oneline
Undo uncommitted changes to a file git restore filename
Undo all uncommitted changes git restore .
Make a branch git checkout -b branch-name
Switch branch git checkout main
Upload to GitHub git push
Download changes git pull

You can ask the AI to run these for you. But learn what they do.

Habits

  1. Commit after every working step. Small commits, clear messages.
  2. Never work on a broken main. Use branches for risky changes.
  3. Commit before asking the AI for a big change. Then you can undo it.
  4. Read the diff. Before committing, look at what the AI changed: git diff. Surprising changes are red flags.
  5. Never commit secrets. See below.

Connect to GitHub

  1. Make a free GitHub account with 2FA. See Accounts and Login.
  2. Click New repository. Choose Private unless you want it public.
  3. Follow the instructions GitHub shows to connect your local project, or ask the AI.
  4. git push to upload.

.gitignore: files Git should never save

Create a file named .gitignore in your project:

node_modules/
.env
.env.local
.env.*.local
.DS_Store
dist/
build/
*.log

.env files hold secrets. Ignoring them is critical. See Secrets and API Keys.

Warning If you accidentally commit a secret

Deleting it in a later commit is NOT enough. It stays in history. Rotate (replace) the secret immediately in the service’s dashboard. Treat it as stolen. Details in Secrets and API Keys.

Good commit messages

  • add login page
  • fix crash when cart is empty
  • update colors to new brand tokens

Pull requests and review

When working with others, or when you want a careful second look, make a pull request (PR). Others (or an AI reviewer) comment before changes merge. GitHub can also run automated checks on each PR.

GitHub features that protect you

  • Secret scanning and push protection: block accidental key uploads.
  • Dependabot: alerts and updates for vulnerable packages.
  • Branch protection: require reviews or checks before merging.
  • Find these in repo Settings and Security.

Databases and Supabase

On this page

What a database is

A database stores information in tables, like spreadsheets. Each row is one item (one user, one order). Each column is one fact (name, email, price).

users table
| id | name | email         |
| 1  | Ava  | ava@mail.com  |
| 2  | Ben  | ben@mail.com  |

Tables connect. An orders table can have a user_id column pointing to a user. This is a relationship.

Without a database your app forgets everything when the page closes.

What Supabase is

Supabase is a service that gives you, ready-made:

  • A Postgres database (a very popular, trusted type)
  • Authentication (sign up, log in, password reset). See Accounts and Login
  • Storage for files like profile pictures
  • Auto-generated APIs so your frontend can talk to the data
  • Edge Functions (small server programs)
  • Realtime updates

It saves you from building a backend from scratch. A free tier exists.

Setup outline

  1. Create an account (with 2FA).
  2. Create a project. Choose a region near your users. Save the database password in your password manager.
  3. Find your Project URL and keys in Project Settings > API.
  4. Create tables in the Table Editor or by asking the AI to write SQL.
  5. Turn on Row Level Security. See Data Access and RLS. This step is not optional.
  6. Add the URL and the anon key to your app’s environment variables. See Secrets and API Keys.

Two keys, very different

Key Where it may be used Power
anon / publishable key In the browser. Public. Limited by your security rules (RLS)
service role / secret key Servers only. Never in the browser, never in Git. Bypasses all rules. Full access to everything.

Warning The classic disaster

Putting the service role key in frontend code, or turning off RLS “to make it work”. Anyone can then read, change, or delete all your data. This happens to real products every year.

Design your tables

Ask the AI, then check:

  • Every table has a primary key id.
  • Every row of private data has an owner column (user_id) or organization column (org_id).
  • Include created_at timestamps.
  • Avoid storing what you do not need. Less data, less risk.
  • Never store passwords yourself. Supabase Auth handles them.

Migrations

A migration is a saved, repeatable change to your database structure. Keep them in your project so you can rebuild the database anywhere. Ask: “Write this as a Supabase migration.”

Local vs production database

Use a separate Supabase project for testing and one for production. Never test on real customer data.

Backups

Free plans have limited backups. Paid plans offer daily backups and point-in-time recovery. See Backups and Recovery.

Alternatives

Firebase, PlanetScale, Neon, Turso, Appwrite, or your own Postgres. The principles (RLS-style rules, secret keys, backups) apply to all.

Prompts

“Design database tables for [app]. For each table, list columns, owner column, and what rules a user should have. Then write the SQL, including Row Level Security policies. Explain each policy in plain English.”

Hosting With Vercel

On this page

What hosting is

Your app on your laptop is visible only to you. Hosting puts it on computers that are always on, so everyone can reach it. This is deploying.

What Vercel is

Vercel is a hosting platform popular for modern web apps (especially Next.js). You connect your GitHub project. Every time you push changes, Vercel automatically builds and publishes. A free tier exists for personal projects; commercial use generally needs a paid plan, so read the current terms.

First deploy

  1. Push your project to GitHub. See Git and GitHub.
  2. Sign up at Vercel using GitHub (with 2FA).
  3. Add New Project, choose your repository.
  4. Vercel detects the framework. Keep defaults.
  5. Add Environment Variables (see below) before deploying.
  6. Click Deploy. In a minute you get a live URL.

Environment variables

Settings like API keys live outside your code. In Vercel: Project Settings > Environment Variables.

Warning Public vs private variables

In many frameworks, variables starting with NEXT_PUBLIC_ (or VITE_, PUBLIC_) are sent to every visitor’s browser. Never put secrets there. Only put things that are safe to be public (like Supabase’s anon key and URL). See Secrets and API Keys.

Set values separately for Production, Preview, and Development. Use different keys for each.

Preview deployments

Every branch and pull request gets its own private test URL. Test there before merging to main. This is your staging area.

Rollbacks

Broke something? In the Vercel dashboard, open Deployments, choose a previous good one, and promote (or “instant rollback”). Back in seconds.

Custom domain

Add your domain in Settings > Domains and follow DNS instructions. HTTPS is set up automatically. See Domains DNS and HTTPS.

Logs and monitoring

  • Runtime logs show errors from server code.
  • Analytics shows visitors.
  • Set up alerts for failed deployments and spend limits.

Costs to watch

Bandwidth, serverless function runtime, image optimization. Set spend limits and usage alerts. See After Launch.

Common problems

Symptom Likely cause
Build fails Read the build log. Often a type error or missing package. Paste it to the AI.
Works locally, blank online Missing environment variable
Login works locally, fails online Wrong redirect URL in Supabase Auth settings
404 on refresh Routing setup mismatch
API calls fail CORS or wrong URL

Alternatives

  • Cloudflare Pages / Workers: see Cloudflare
  • Netlify, Render, Railway, Fly.io
  • A VPS (virtual private server) if you want to manage things yourself. More control, more responsibility, more security work.

Domains, DNS, and HTTPS

On this page

Domain name

Your address: mycoolapp.com. You rent it yearly from a registrar (Cloudflare, Namecheap, Porkbun, Google-successors, etc.).

Choosing

  • Short, easy to spell and say aloud
  • .com if possible; others are fine
  • Search for trademark conflicts before committing
  • Keep it renewed. Turn on auto-renew and keep a valid payment method.
  • Turn on registrar lock and 2FA. If someone steals your domain, they steal your product.

DNS: the phone book

DNS translates mycoolapp.com into the real address of your server. You edit it with records:

Record Purpose Example
A Name to an IPv4 address @ → 76.76.21.21
AAAA Name to an IPv6 address
CNAME Name to another name www → cname.vercel-dns.com
MX Where email goes Points to your email provider
TXT Text notes. Used to prove ownership and for email security SPF, DKIM, verification codes

@ means “the bare domain”. Your host (Vercel, etc.) tells you exactly which records to add.

Changes can take minutes to hours to spread (propagation). Be patient.

HTTPS

The https:// and padlock mean traffic between visitor and site is encrypted. Without it, strangers on the same Wi-Fi can read or alter what is sent, and browsers warn “Not secure”.

Your host or Cloudflare gives you a free certificate automatically. Make sure:

  • All traffic redirects from http to https.
  • Your site does not load images or scripts over plain http (called mixed content).

Email for your domain

  • Sending email from your app (receipts, password resets) needs an email provider and proper SPF, DKIM, DMARC DNS records, or your mail lands in spam. Providers walk you through it. See Common Services.
  • Receiving: Cloudflare Email Routing, Google Workspace, Proton, Fastmail.

Subdomains

app.mycoolapp.com, api.mycoolapp.com, staging.mycoolapp.com. Great for separating marketing site, app, and test environment.

Security Mindset

On this page

Why this matters

Once your app is on the internet, automated bots find it within hours and probe it. They are not targeting you personally. They scan millions of sites for easy mistakes. If you leave a door unlocked, they walk in.

AI writes code that works, not code that is safe. It often skips security because you did not ask. Security is your job.

The house analogy

House App
Front door lock Login. See Accounts and Login
Spare key under the mat Secret keys left in code. See Secrets and API Keys
Rooms guests may not enter Authorization and data rules. See Data Access and RLS
Windows Every form and input. See Common Attacks
Fire extinguisher and insurance Backups. See Backups and Recovery
Neighbors who watch Monitoring. See After Launch

Core principles

1. Never trust the browser

Everything the user’s browser sends can be faked. Hiding a button is not security. Check permissions on the server and in the database.

2. Least privilege

Give each person, key, and program the minimum access needed. Not admin by default.

3. Defense in depth

Several layers. If one fails, another still protects you: login, server checks, database rules, firewall, monitoring.

4. Secure by default

New tables locked. New files private. New features off for others until intended.

5. Collect less

Data you never collected cannot leak. Do not ask for a birthday if you do not need it.

6. Assume you will make mistakes

Plan for them: backups, logs, ability to rotate keys, a way to roll back.

7. Keep things updated

Old packages have known holes. Update regularly. See Reviewing AI Code.

8. Trust, but verify

Verify every important claim the AI makes. Verify every package it adds.

What attackers want

  • Your data (emails, passwords, personal info) to sell or misuse
  • Your money (stolen payments, running up your cloud bill, crypto mining)
  • Your accounts (to spam from)
  • Your reputation (defacement)
  • Your users’ trust

Risk thinking

Ask for each feature:

  1. What is the worst thing that could happen here?
  2. Who could do it?
  3. What stops them?

Write answers in your notes. Higher stakes (money, health, children, other companies’ data) require stronger protection. See Priorities Compared.

Using AI against its own mistakes

Use a fresh conversation as a security reviewer. See the security prompt in Prompt Library. Do not rely on one review. Do several.

The three-step habit

  1. Build.
  2. Break. Try to misuse your own app.
  3. Review. Use Security Checklist.

Secrets and API Keys

On this page

What is a secret?

Anything that lets someone act as you or your app:

  • API keys and tokens
  • Database passwords
  • Service role keys
  • Webhook signing secrets
  • Private encryption keys
  • Your own passwords

An API key is a password for a program. If a stranger gets it, they can spend your money and read your data.

Rule 1: Secrets never go in code

Not in files you commit. Not in comments. Not in screenshots. Not in chats with the AI.

Where they live instead: environment variables

Environment variables are settings stored outside your code.

Locally, in a file named .env.local (or .env):

SUPABASE_URL=https://xyz.supabase.co
SUPABASE_ANON_KEY=public-key-here
SUPABASE_SERVICE_ROLE_KEY=never-share-this
STRIPE_SECRET_KEY=sk_live_never-share

Your code reads them: process.env.STRIPE_SECRET_KEY.

Online, set them in your host’s dashboard. See Hosting With Vercel.

Rule 2: .gitignore your .env files

Add to .gitignore:

.env
.env.*
!.env.example

Commit a .env.example that lists the names with fake values, so you remember what is needed:

SUPABASE_URL=
SUPABASE_ANON_KEY=
SUPABASE_SERVICE_ROLE_KEY=

See Git and GitHub.

Rule 3: Public versus private

Safe in browser (public by design) Must stay on the server
Supabase URL and anon key Supabase service role key
Stripe publishable key Stripe secret key and webhook secret
Turnstile site key Turnstile secret key
Analytics ID AI provider API keys
Database connection strings

Variables prefixed NEXT_PUBLIC_, VITE_, or PUBLIC_ get shipped to every visitor.

Warning “It’s hidden in my JavaScript” is not hidden

Anyone can open browser tools and read all frontend code. If a key must be secret, only server code may use it.

Rule 4: Keep secrets out of AI chats

Do not paste real keys into prompts. Replace with YOUR_KEY_HERE. Some tools can read your .env automatically; check settings and exclude it where you can.

Rule 5: Different keys per environment

Test keys for development. Live keys only on production. A leaked test key hurts little.

Rule 6: Limit each key

Many services let you restrict a key to certain actions, IP addresses, or websites. Use the narrowest option. Set spending limits.

If a secret leaks

Act fast. Assume it is stolen.

  1. Rotate it: create a new key in the service dashboard, delete the old one.
  2. Update the new key in your hosting environment.
  3. Check the service’s usage logs for strange activity.
  4. Check bills.
  5. Remove it from the code, but know history still contains it. Rotating is what fixes it.
  6. If personal data may be exposed, see Privacy and Legal.

Scan for leaks

  • GitHub secret scanning and push protection
  • gitleaks or trufflehog to scan your history
  • Prompt: “Search the entire project for hardcoded keys, tokens, and passwords.”

Password manager

Use one (Bitwarden, 1Password). Store service passwords and recovery codes there. Never in a plain text file on your desktop.

Accounts and Login

On this page

Two separate jobs:

  • Authentication: Who are you? (logging in)
  • Authorization: What may you do? (permissions)

Protect YOUR accounts first

Your hosting, database, domain, email, and GitHub accounts control the whole product.

  • Unique, long password for each (use a password manager)
  • 2FA on everything. Prefer an authenticator app or a passkey or hardware key. SMS is the weakest.
  • Save recovery codes offline
  • Use an email address only you control, and secure it most of all
  • Review who has access regularly. Remove old collaborators.
  • Check if your email appeared in a breach: Have I Been Pwned

Rule: never build your own login

Storing passwords correctly, handling resets, blocking guessing attacks, and managing sessions are all hard. Use:

  • Supabase Auth, Clerk, Auth0, Firebase Auth, or your framework’s trusted library
  • Social login (Google, Apple) so you never see a password
  • Magic links or passkeys for passwordless

If the AI starts writing code that stores passwords itself, stop and ask for a standard auth service.

What good login includes

Authorization: who may do what

Define roles:

  • Owner/Admin: everything
  • Member: normal use
  • Viewer: read only
  • Anonymous: only public pages

And ownership: “A user may only edit their own items.”

The most common vibe-coding security failure: the app checks you are logged in, but never checks the item belongs to you. Then user 5 can change the web address to /orders/6 and see someone else’s order. Defend this at the database level. See Data Access and RLS.

Admin pages

  • Hidden URL is not protection. Require admin role checked on the server.
  • Log admin actions.
  • Avoid shared admin accounts.

Sessions and tokens (in plain words)

After login, the browser holds a token, like a wristband at a concert. The server checks it on each request. Keep tokens in secure cookies, set to expire. Do not store sensitive tokens where scripts can read them if your auth tool offers safer options.

Test your login

  • Log out, then try to open a private page by URL
  • Log in as user A, try to load user B’s data
  • Try wrong passwords 20 times. Are you slowed down?
  • Try the reset link twice

Data Access and RLS

On this page

The problem

In modern apps, the browser often talks directly to the database service. That is only safe if the database itself decides who may see what. Otherwise anyone can ask for everything.

Row Level Security (RLS)

RLS is a set of rules inside the database: “A row can be seen only by the person who owns it.” Every request is checked automatically, whatever the app code does.

Think of a filing cabinet where each drawer has its own lock, and your key only fits your drawer.

The rules

  1. Turn RLS on for every table that holds anything not meant for the public.
  2. With RLS on and no policies, nobody can access anything. That is the safe default. Add policies for exactly what is needed.
  3. Write separate policies for reading, inserting, updating, and deleting.
  4. Test as different users, including logged out.
  5. Never use the service role key in the browser. It ignores RLS. See Secrets and API Keys.

Example in plain English

Table notes with a user_id column.

  • Read: a user may read notes where user_id equals their own id.
  • Insert: a user may add notes only with their own id.
  • Update/Delete: only their own notes.

In SQL (Supabase):

alter table notes enable row level security;

create policy "Users read own notes"
  on notes for select
  using (auth.uid() = user_id);

create policy "Users insert own notes"
  on notes for insert
  with check (auth.uid() = user_id);

create policy "Users update own notes"
  on notes for update
  using (auth.uid() = user_id);

create policy "Users delete own notes"
  on notes for delete
  using (auth.uid() = user_id);

Ask the AI to write these, then ask it to explain each policy in plain English and list what a stranger can do.

Multi-tenant data (company products)

For apps with organizations: every row has org_id. Policies allow access only if the user is a member of that org with the right role. Mistakes here leak one company’s data to another. See Company Products.

Public data

Some things should be public (blog posts). Make a policy that says so explicitly, for read only.

Files

Storage buckets also have rules. Make buckets private by default. Use short-lived signed links for sharing.

Test checklist

How to test: use two test accounts, or run queries as different users in the Supabase SQL editor, or ask the AI to write tests.

Even without Supabase

Any database needs the same idea: the server must check ownership on every request, never trust IDs sent from the browser. See Common Attacks (broken access control).

Prompt

List every table and storage bucket. For each: is RLS on, what each policy allows, and what an anonymous user and a different logged-in user can do. Flag any gaps.

Common Attacks

On this page

Plain-English versions of the most common web attacks, based on the OWASP Top Ten (the industry’s list of the most serious risks). You are not expected to write defenses by hand. You are expected to know the names so you can ask the AI to defend against them and check that it did.

1. Broken access control

What: Users do things they are not allowed to. Example: changing /invoice/12 to /invoice/13 and seeing someone else’s invoice. Defense: Check ownership on the server and in database rules. See Data Access and RLS. Most common serious flaw.

2. Exposed secrets and misconfiguration

What: Keys in code, debug mode left on, open storage buckets, default passwords. Defense: Secrets and API Keys, Security Checklist.

3. Injection (SQL injection)

What: An attacker types database commands into a form field. If your code pastes user text into a database command, they take over the query. Example input: '; DROP TABLE users; -- Defense: Use parameterized queries (or the database library’s safe functions). Never build queries by gluing strings. Ask: “Confirm no SQL is built by string concatenation.”

4. Cross-site scripting (XSS)

What: An attacker gets their own JavaScript to run in other users’ browsers, by posting something like a comment containing a script. Defense: Modern frameworks (React) escape text by default. Danger signs: dangerouslySetInnerHTML, innerHTML, v-html. If you must show user-written HTML, sanitize it with a trusted library. Add a Content Security Policy header.

5. Cross-site request forgery (CSRF)

What: A malicious website tricks a logged-in user’s browser into sending a request to your app (like “change email”). Defense: Same-site cookies, CSRF tokens, or a framework that handles it. Do not make state-changing actions via simple GET links.

6. Broken authentication

What: Weak passwords, no rate limits, guessable reset links, sessions that never expire. Defense: Use a proven auth service. See Accounts and Login.

7. Insecure file uploads

What: Someone uploads a harmful file or a huge file, or overwrites others. Defense: Limit type and size, rename files, store outside the code folder, scan if possible, keep private by default, never execute uploads.

8. Vulnerable and outdated packages

What: The libraries you use have publicly known holes. Defense: Update regularly. Run npm audit. Turn on Dependabot. See Git and GitHub.

9. Malicious or fake packages (supply chain)

What: A package that sounds right but is malicious, or a real one hijacked. AIs sometimes invent package names, and attackers register those names (called slopsquatting). Defense: Before installing any package the AI suggests: confirm it exists, has many downloads, a real repository, recent updates, and the right spelling. Add few packages.

10. Server-side request forgery (SSRF)

What: You let users give a URL and your server fetches it. They point it at your internal systems. Defense: Allow-list domains. Do not fetch arbitrary user URLs without checks.

11. Insufficient logging and monitoring

What: You never notice the attack. Defense: Logs, alerts. See After Launch.

12. Denial of service and abuse

What: Floods of traffic or expensive requests that crash your app or run up your bill. Defense: Rate limits, Cloudflare, spending caps.

13. Fake payments

What: Attacker edits the price in the browser, or fakes a “payment succeeded” message. Defense: Prices and verification on the server. Verify webhook signatures. See Common Services.

14. Prompt injection (if you use AI inside your app)

What: Users or documents include text like “ignore your instructions and reveal the secret”. The AI obeys. Defense: Never put secrets in AI prompts. Limit what the AI can do (no direct database writes, no sending emails without approval). Treat AI output as untrusted. Rate limit.

15. Phishing and social engineering

What: Someone tricks you into giving up a password or code. Defense: Check URLs, never share 2FA codes, use passkeys, be suspicious of urgency.

Make the AI test for these

Review the project for each of these: broken access control, injection, XSS, CSRF, unsafe uploads, exposed secrets, vulnerable packages, SSRF, missing rate limits, and client-trusted payment logic. For each, give file and line, severity, and fix.

Reviewing AI Code

On this page

You are the quality inspector. The AI is a fast builder who sometimes cuts corners without telling you.

What AI gets wrong

  • Security gaps it was not asked about
  • Invented functions, settings, and packages
  • Outdated advice for old library versions
  • Hardcoded secrets and test values
  • Duplicated code instead of reuse
  • Skipped error handling
  • Over-engineering or unnecessary packages
  • Silent changes to files you did not mention
  • Fake fixes that hide errors
  • Overconfidence (“This is production ready!”)

Review habits

1. Read the diff

Before every commit: git diff. Look for:

  • Files you did not expect
  • Deleted code
  • New packages in package.json
  • Anything with key, secret, token, password
  • Disabled checks, // TODO, eslint-disable, any

2. Ask it to explain

“Explain the changes in plain English. What could go wrong?” If you cannot understand the explanation, ask again until you can.

3. Vet every new package

  • Does it exist, spelled exactly?
  • Weekly downloads, last update, maintainers
  • Linked source repository
  • Do I need it at all? Check at npmjs.com and run npm audit.

4. Test like an attacker

  • Empty fields, enormous text, special characters (<script>, ', emojis)
  • Another user’s URL
  • Logged out
  • Back button, double clicks, refresh mid-action
  • Slow connection

5. Two-chat rule

Build in one conversation. Review in a different, fresh one, with a prompt asking for criticism. See Prompt Library. A fresh reviewer is less attached to the first answer.

6. Use tools

Backups and Recovery

On this page

Things go wrong: a bad AI command deletes a table, an account is hacked, a service shuts down, you make a typo. A backup you have never restored is only a hope.

What to back up

Thing How
Code Git plus GitHub. See Git and GitHub
Database Supabase backups (paid plans: daily and point-in-time), plus your own exports
Uploaded files Storage bucket copies
Configuration and secrets Password manager and a secure note of what variables exist (not values in Git)
Notes and plans Obsidian vault in a synced or Git-tracked folder
DNS records Export them from Cloudflare
Design files Figma versions, exports

The 3-2-1 rule

  • 3 copies of important data
  • 2 different kinds of storage
  • 1 copy somewhere else (offsite)

Automate

Manual backups get forgotten. Schedule them. Paid database plans do it for you. Otherwise use scheduled exports.

Test a restore

At least once before launch, and after big changes:

  1. Create a blank test project.
  2. Restore the backup into it.
  3. Confirm the app works with that data. Write down the steps and how long it took.

Protect the backups

Backups contain all your data. Encrypt them, restrict access, delete old ones you no longer need. See Privacy and Legal.

Recovery plan

Write a short note called If everything breaks:

  1. How to roll back a deployment. See Hosting With Vercel
  2. How to restore the database
  3. Where the keys and logins are
  4. Who to contact (hosting support, a friend who helps)
  5. How to tell users

Before risky AI actions

  • Commit first.
  • Export the database before running AI-generated migrations or deletions.
  • Be extra careful when the AI runs commands on a live database. Prefer testing on a copy.

Privacy and Legal

On this page

Warning Not legal advice

This is general education. Laws differ by country, state, and industry. For anything commercial, consult a qualified lawyer or use reputable policy generators and have them reviewed.

Why it matters

When you collect other people’s information, you take on legal duties. Fines can be large. Trust, once lost, is hard to regain.

Know what you collect

Make a list in your notes:

Data Why needed Where stored Who can see it How long kept
Email Login Supabase Me Until account deleted

Personal data includes names, emails, phone numbers, addresses, IP addresses, photos, location, and anything that identifies a person.

Sensitive data (health, finance, children’s data, precise location, government IDs, biometrics) carries extra rules. Avoid collecting it unless truly necessary, and get professional guidance first.

Principles

  • Collect the minimum.
  • Say what you collect and why. Plainly.
  • Get consent where required.
  • Let people see, export, correct, and delete their data.
  • Secure it. See the rest of Security Checklist.
  • Keep it only as long as needed.
  • Tell people if there is a breach, as laws require.

Pages you will usually need

  1. Privacy Policy: what you collect, why, who it is shared with, how to contact you.
  2. Terms of Service: rules for using your product, payments, limits of liability.
  3. Cookie notice/consent: if you use non-essential cookies or tracking, in places that require it.
  4. Refund policy: if you charge money.
  5. Contact/support page.

Link them in your footer and at signup.

Key laws to know exist

Law Where Short idea
GDPR European Union / UK Strong rights over personal data; applies if you serve people there
CCPA/CPRA California Right to know, delete, and opt out of sale
COPPA United States Strict rules for children under 13
HIPAA United States Health information
PCI DSS Global (card industry) Card data; using Stripe Checkout keeps you mostly out of scope
CAN-SPAM, CASL US, Canada Email marketing rules
ADA, EAA, WCAG Various Accessibility. See Accessibility

Warning Children

If your product might be used by children, the rules become strict. Get proper guidance before collecting anything from minors.

Third parties

Every service you use (hosting, analytics, AI, email) may receive user data. List them in your Privacy Policy. Check their data terms. For company customers, you may need a Data Processing Agreement. See Company Products.

AI and privacy

  • Do not send users’ personal data to AI services unless your policy and their terms allow it.
  • Check whether the provider trains on your data.
  • Never paste customer data into a casual AI chat while building.

Open-source and copyright

  • Check licenses of packages and images you use.
  • Do not copy other products’ code, text, or branding.
  • You are responsible for what you publish even if an AI generated it.

If there is a breach

  1. Contain it: rotate keys, revoke access. See Secrets and API Keys.
  2. Find out what was exposed.
  3. Notify affected users and authorities where required, often within days.
  4. Fix the cause. Write down lessons.
